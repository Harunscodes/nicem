# Token-Tax vs. Execution-Tax — Definitions and Distinctions

This document establishes the canonical NiceM definitions for these two concepts and explains why the distinction matters.

---

## Token-Tax

### Definition

Token-tax is the cost premium paid when a tokenization system produces more tokens for a given unit of semantic content in certain languages, scripts, or input types than in others.

### Origin

The term comes from the NLP fairness literature. It is documented and named in Lundin and Ahia et al., and empirically measured in Petrov et al. and related work.

### Mechanism

1. LLM vocabularies are built from training corpora dominated by English and other high-resource languages.
2. Characters and subwords from underrepresented scripts are split into more pieces.
3. Equivalent meaning in an underrepresented language produces a longer token sequence.
4. API pricing is per-token, so longer sequences cost more.
5. Result: users in underrepresented languages pay more per unit of meaning.

### Where it occurs

At the **tokenization layer** — before inference begins.

### Who it affects

Any user whose input language, script, or content type tokenizes inefficiently relative to the model's vocabulary.

### Status

**Established concept** — documented in the academic literature.

---

## Execution-Tax

### Definition

*(NiceM hypothesis)* Execution-tax is the additional token and compute overhead generated by the structure of agentic, multi-step AI workloads — beyond what the core task semantically requires.

### Proposed mechanism

In a multi-step agentic workflow, tokens are produced not just for task content but for:
- System prompts repeated at each step
- Tool-call formatting and response scaffolding
- Context re-tokenization across agent boundaries
- Orchestration instructions that carry no semantic payload for the end user
- Error recovery and retry loops

These tokens are billed, consumed compute, and consume context window — but they represent structural overhead, not task content.

### Where it occurs

At the **execution layer** — during inference, across the architecture of a multi-step workload.

### Who it affects

Any operator or user running agentic, multi-step, or orchestrated AI workloads.

### Status

**NiceM hypothesis — not yet proven.** Requires:
- Measurement of overhead token share in real agentic workloads
- Comparison across workload architectures
- Evidence that overhead is reducible without degrading task quality

---

## Key Distinctions

| | Token-Tax | Execution-Tax |
|---|---|---|
| **Origin** | Tokenization vocabulary construction | Workload architecture |
| **Layer** | Tokenization (pre-inference) | Execution (during inference) |
| **Cause** | Language/script underrepresentation | Orchestration and scaffolding overhead |
| **Evidence** | Established in literature | NiceM hypothesis |
| **Affects** | Users by language/script | Operators/users by workload design |
| **Reducible by** | Better tokenizers, vocabulary expansion | Better workload architecture |

---

## Why both matter for NiceM

The two taxes are independent in origin but compound in effect. A user running an agentic workflow in an underrepresented language pays token-tax on every token produced — including every overhead token generated by execution-tax. The combined cost burden is higher than either effect alone, and currently invisible in standard API pricing.

NiceM's argument is that making both effects measurable and attributable is the first step toward addressing them.

---

## What this document does not claim

- That execution-tax has been measured (it has not yet)
- That the two taxes are caused by the same mechanism
- That either tax is intentional
- That token-tax and execution-tax are the only sources of AI cost inequality
